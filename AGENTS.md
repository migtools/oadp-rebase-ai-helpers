# AGENTS.md - Guide for AI Coding Agents

This guide helps AI coding agents navigate and contribute to the oadp-rebase-ai-helpers repository, which contains Claude Code plugins for automating OADP (OpenShift API for Data Protection) rebase workflows.

## Repository Overview

This repository contains Claude Code plugins for OADP rebase operations, organized under the `plugins/` directory. The primary plugin (`oadp-rebase`) provides slash commands for automating the process of rebasing downstream OpenShift forks of the Velero ecosystem to newer upstream versions.

## Domain Knowledge: OADP Rebase Process

### What is OADP?
OADP (OpenShift API for Data Protection) is a Red Hat product wrapping the upstream Velero backup/restore project for OpenShift. The OADP team maintains ~20 downstream forks containing OpenShift-specific patches.

### What is a Rebase?
A rebase updates a downstream fork to a newer upstream version while preserving downstream-only patches. The rebasebot tool automates this by:
1. Starting from the new upstream tag (the "source")
2. Cherry-picking `UPSTREAM: <carry>` commits from the downstream branch (the "dest")
3. Running post-rebase hook scripts (go mod replace, tidy, vendor, etc.)
4. Pushing the result and creating a PR

### Critical Safety Rules
1. **ALWAYS verify carry commits** after every rebase - never assume they were preserved
2. **ALWAYS rebase in wave order** (1 -> 2 -> 3 -> 4 -> 5) - later waves depend on earlier ones
3. **NEVER leave `--conflict-policy warn` in config files** - only use it temporarily for a single run
4. **Check for stale rebase branches** if a PR shows unexpected file deletions
5. **`UPSTREAM: <carry>` commits are sacred** - losing one is a critical failure
6. **`UPSTREAM: <drop>` commits are disposable** - they are regenerated by hooks each rebase

### Wave Ordering
| Wave | Repositories | Why This Order |
|------|-------------|----------------|
| 1 | kopia, restic, filebrowser, oadp-vmdp | No velero dependency |
| 2 | velero | Depends on kopia (Wave 1) |
| 3 | velero plugins, kubevirt-velero-plugin, oadp-operator | Depend on velero (Wave 2) |
| 4 | oadp-non-admin, openshift-velero-plugin, datamover-controller | Depend on Wave 3 |
| 5 | oadp-must-gather, oadp-cli, datamover-plugin | Depend on Wave 4 |
| Special | hypershift-oadp-plugin | Always manual, depends on Wave 2 |

### Two Rebase Patterns
1. **Full rebase** (source != dest): Upstream -> Downstream (e.g., velero-io/velero:v1.18.1 -> openshift/velero:oadp-1.6)
2. **Hooks-only** (source == dest): Same repo, just runs hooks (e.g., oadp-operator, velero-plugin-for-legacy-aws)

### Config Files
Located in `rebase-configs/` of the oadp-rebase repo:
```
{org}_{repo}_{branch}.env.sh
```
Key variables: `SOURCE_UPSTREAM_REPO`, `DESTINATION_DOWNSTREAM_REPO`, `REBASE_REPO`, `HOOK_SCRIPTS`, `EXTRA_REBASEBOT_ARGS`

### Upstream Org Migration: vmware-tanzu -> velero-io
The upstream Velero repos moved from `vmware-tanzu` to `velero-io` on GitHub. Config files use `velero-io` for git URLs. However, the Go module path in go.mod may still be `github.com/vmware-tanzu/velero` - these are independent identifiers. Hook scripts dynamically detect which module path each project uses. See the rebase-workflow skill for full details.

### Hook Scripts
Post-rebase scripts in `rebasebot-hook-scripts/`:
- `go-replace_velero_{branch}.sh` - Add replace for the velero module (auto-detects vmware-tanzu or velero-io from go.mod)
- `go-replace_kopia_{branch}.sh` - Replace kopia/kopia with migtools/kopia
- `go-mod-tidy-and-commit.sh` - Run go mod tidy and vendor
- `normalize-dockerfiles-and-commit.sh` - Normalize Dockerfile formatting
- `restic-submodule-and-commit_{branch}.sh` - Update restic submodule (velero only)
- `oadp-operator-copy-crds-from-velero-and-commit_{branch}.sh` - Copy CRDs (operator only)
- `oadp-operator-run-make-bundle-and-commit.sh` - Run make bundle (operator only)

### Common Failure Modes
1. **Stale rebase branch**: Rebasebot uses old branch, drops downstream files. Fix: delete remote branch, manually create from dest.
2. **Strict conflict policy blocking**: go.mod content from `<drop>` commits flagged. Fix: temporarily use `--conflict-policy warn`.
3. **Cherry-pick conflicts**: Downstream patches conflict with upstream. Fix: manual cherry-pick and conflict resolution.
4. **Missing dependency**: Wave ordering violated, go mod tidy fails. Fix: rebase dependencies first.

## Plugin Conventions

### Skill Definition Format
Slash commands are defined directly by `plugins/{plugin-name}/skills/{skill-name}/SKILL.md`:

```markdown
---
description: Brief description
argument-hint: [optional] [arguments]
---

## Name
plugin-name:command-name

## Synopsis
## Description
## Implementation
## See Also
```

### Skills (source of truth)
All command implementations and reusable procedures live in `plugins/{plugin-name}/skills/{skill-name}/SKILL.md`.

## Contributing

### Adding a New Command
1. Create `plugins/oadp-rebase/skills/{command-name}/SKILL.md` with the full implementation
2. Update PLUGINS.md

### Adding a New Skill
1. Create `plugins/oadp-rebase/skills/{skill-name}/SKILL.md`
2. Document step-by-step procedures
3. Include error handling and debugging

### Best Practices
1. **Be explicit**: Don't assume knowledge of OADP internals
2. **Provide complete commands**: Include full bash commands with paths
3. **Handle edge cases**: Document failure modes and recovery
4. **Include prerequisites**: List required tools and access
5. **Show real examples**: Use actual repo names, tags, and branches
6. **Cross-reference**: Link to related commands and skills
