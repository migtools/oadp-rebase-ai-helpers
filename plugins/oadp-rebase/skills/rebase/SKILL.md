## Name
oadp-rebase:rebase

## Synopsis
```
/oadp-rebase:rebase <repo-branch|wave-number> [--branch <oadp-branch>] [--dry-run]
```

## Description
The `oadp-rebase:rebase` command executes the OADP rebase process for either a single repository or an entire wave of repositories. It uses the `run-oadp-rebase.sh` script and rebasebot to cherry-pick downstream commits onto new upstream base tags/branches.

OADP (OpenShift API for Data Protection) maintains downstream forks of the Velero backup/restore ecosystem. Each fork contains downstream-only patches (marked with `UPSTREAM: <carry>` commit prefixes) that must be preserved across rebases to newer upstream versions. The rebasebot tool automates this by:

1. Starting from the new upstream tag/branch (the "source")
2. Cherry-picking all `UPSTREAM: <carry>` commits from the downstream branch (the "dest")
3. Running post-rebase hook scripts (go mod replace, tidy, vendor, Dockerfile normalization, etc.)
4. Pushing the result to a rebase branch and creating a PR

### What is OADP?
OADP is a Red Hat product that wraps the upstream Velero project for OpenShift. The OADP team maintains downstream forks of ~20 repositories across the Velero ecosystem. These forks add OpenShift-specific patches, Konflux/Tekton CI integration, custom Dockerfiles, and dependency replacements (e.g., pointing to downstream velero instead of upstream velero). Note: upstream Velero repos moved from the `vmware-tanzu` GitHub org to `velero-io`, but the Go module path may still use `github.com/vmware-tanzu/velero` - these are independent identifiers.

### What is Rebasebot?
Rebasebot is a Go tool (available as container image `quay.io/migtools/rebasebot:latest` or CLI binary) that automates the rebase process. It:
- Clones source (upstream), dest (downstream), and rebase (working) repositories
- Identifies downstream commits to preserve — it uses merge history to find them, not just the `UPSTREAM: <carry>` prefix. Commits without the prefix are ALSO identified and cherry-picked.
- Cherry-picks them onto the new upstream base
- Runs post-rebase hook scripts
- Pushes the result and creates a PR

### Wave Ordering
Repositories MUST be rebased in wave order because later waves depend on earlier ones:

- **Wave 1**: kopia, restic, filebrowser, oadp-vmdp (no velero dependency)
- **Wave 2**: velero (depends on kopia from Wave 1)
- **Wave 3**: velero plugins (aws, gcp, azure, legacy-aws, csi), kubevirt-velero-plugin, oadp-operator (depend on velero from Wave 2)
- **Wave 4**: oadp-non-admin, openshift-velero-plugin, kubevirt-datamover-controller, oadp-vm-file-restore (depend on Wave 3)
- **Wave 5**: oadp-must-gather, oadp-cli, kubevirt-datamover-plugin (depend on Wave 4)

### Two Rebase Patterns

1. **Full upstream rebase** (source != dest): Cherry-picks downstream commits onto new upstream tag
   - Example: velero rebased from `velero-io/velero:v1.18.1-rc.1` to `openshift/velero:oadp-1.6`

2. **Hooks-only rebase** (source == dest): No actual rebase; just runs hook scripts to update dependencies
   - Example: oadp-operator (downstream-only repo) runs hooks to update velero CRDs and go.mod replaces
   - Example: velero-plugin-for-legacy-aws (downstream-only) runs hooks to update velero dependency

## CRITICAL: Automation Principles

**DO NOT ask the user for permission at decision points that can be automated.** This skill should execute end-to-end with minimal human interaction. Specifically:

1. **Always run dry-run first** — do not ask "should I do a dry-run?", just do it.
2. **Always inventory downstream commits before rebase** — do not ask, just do it.
3. **Always verify downstream commits after rebase** — do not ask, just do it.
4. **If dry-run fails, analyze the failure and take the appropriate automated action**:
   - If `UPSTREAM: <drop>` commits cause conflicts → this is expected. Use `--conflict-policy warn` temporarily (revert after). Do NOT ask the user. But CAREFULLY review all WARNING lines from the output (see "Scrutinizing `--conflict-policy warn`" below).
   - If cherry-pick conflicts are in go.mod/go.sum only → these are regenerated by hooks, safe to override with `--conflict-policy warn`. Do NOT ask the user.
   - If cherry-pick conflicts are in actual code files → STOP and report to user with details. This requires human judgment.
   - If stale rebase branch is detected → delete it and retry. Do NOT ask the user.
5. **If rebase succeeds but verification finds missing carry commits** → STOP and report. Do NOT push or create PR.
6. **Never skip verification** — even if the rebase appears successful, always compare pre/post commit inventories.
7. **NEVER assume anything is safe to drop.** Every downstream commit and file must be accounted for. Err on the side of caution — it is always better to stop and ask than to silently lose a downstream patch.

**The only times to stop and ask the user are:**
- Code-level cherry-pick conflicts that require understanding the downstream patch intent
- Verification failure (missing carry commits or downstream files)
- Uncertainty about whether a commit is safe to drop
- `--conflict-policy warn` output shows warnings about files OTHER than go.mod/go.sum

### Scrutinizing `--conflict-policy warn`

When using `--conflict-policy warn`, rebasebot prints WARNING lines for every piece of content it considers "lost" during cherry-pick. **You MUST read and classify EVERY warning line**, not just the first few:

- **Safe to ignore**: Warnings about `go.mod` and `go.sum` lines — these are regenerated by `go mod tidy` hook.
- **MUST INVESTIGATE**: Warnings about ANY other file (*.go, Dockerfile*, *.yaml, *.sh, etc.). These could mean a downstream patch is being silently dropped.
- **MUST INVESTIGATE**: Warnings mentioning files that are downstream-only (Dockerfile.ubi, konflux.Dockerfile, .tekton/*, DOWNSTREAM_OWNERS, release-announcement). These files do not exist upstream and must never be deleted.

If ANY warning references a file other than go.mod/go.sum, **STOP and report to the user** with the full warning details before proceeding to the full run. Do NOT assume it's safe.

## Implementation

### Phase 1: Validate Configuration

1. **Set up the oadp-rebase repository**. Do NOT rely on it being in the current working directory or home directory. Re-use a previous clone if available, otherwise clone fresh:
   ```bash
   OADP_REBASE_DIR="/tmp/oadp-rebase-tools"
   if [ -d "$OADP_REBASE_DIR/.git" ]; then
     cd "$OADP_REBASE_DIR"
     git fetch origin
     git reset --hard origin/oadp-dev
   else
     git clone https://github.com/oadp-rebasebot/oadp-rebase.git "$OADP_REBASE_DIR" --branch oadp-dev --single-branch
     cd "$OADP_REBASE_DIR"
   fi
   ```
   This ensures the latest configs and hook scripts are used while saving bandwidth across multiple repo rebases. This directory contains `run-oadp-rebase.sh`, `rebase-configs/`, and `rebasebot-hook-scripts/`. All subsequent commands in Phase 3 should run from this directory.
2. Identify the target: single repo (e.g., `velero-oadp-1.6`) or wave number (e.g., `3`)
3. Load the configuration file from `rebase-configs/` to verify:
   - `SOURCE_UPSTREAM_REPO` - upstream repo and tag/branch
   - `DESTINATION_DOWNSTREAM_REPO` - downstream fork and branch
   - `REBASE_REPO` - working branch for PRs
   - `HOOK_SCRIPTS` - post-rebase hook scripts to run
   - `EXTRA_REBASEBOT_ARGS` - additional flags (e.g., `--always-run-hooks`)
4. Verify the upstream tag/branch exists (curl the GitHub API)
5. Check that secrets directory exists with required keys (`~/.rebasebot/secrets/`)
6. Check that a container engine (docker or podman) is available — required for container mode
7. Print a brief config summary and proceed immediately — do not wait for confirmation.

### Phase 2: Pre-Rebase Inventory (AUTOMATED — do not ask)
This phase MUST happen automatically before every rebase. Do NOT skip it.

1. **Clone the dest repo and identify ALL downstream-only commits**:
   ```bash
   # Clone dest
   git clone https://github.com/{dest-org}/{repo}.git /tmp/oadp-pre-rebase-{repo}
   cd /tmp/oadp-pre-rebase-{repo}
   git checkout {branch}
   # Add upstream remote
   git remote add upstream https://github.com/{upstream-org}/{repo}.git
   git fetch upstream {upstream-branch}
   # List ALL downstream-only commits (everything not in upstream)
   git log --oneline upstream/{upstream-branch}..{branch}
   # Separately identify carry and drop commits
   git log --oneline --grep="UPSTREAM: <carry>" {branch}
   git log --oneline --grep="UPSTREAM: <drop>" {branch}
   ```
2. **Save the FULL downstream commit list** — every single commit, not just carry commits. Store commit messages (not hashes — hashes change during cherry-pick).
3. **Inventory downstream-only files** — files that exist in dest but NOT in upstream:
   ```bash
   # Get list of files only in downstream (not in upstream)
   diff <(git ls-tree -r --name-only upstream/{upstream-branch} | sort) \
        <(git ls-tree -r --name-only {branch} | sort) | grep '^>' | sed 's/^> //'
   ```
   Common downstream-only files to watch for:
   - `Dockerfile.ubi` or `Dockerfile` (if different from upstream)
   - `konflux.Dockerfile`
   - `.tekton/` directory and all files within
   - `release-announcement`
   - `DOWNSTREAM_OWNERS`
   - Any `*.ubi.*` files
   Save this list — every one of these files MUST exist after rebase.
4. **Classify commits**:
   - `UPSTREAM: <carry>` → MUST be preserved (manually authored downstream patches)
   - `UPSTREAM: <drop>` → safe to lose (regenerated by hooks each rebase)
   - No prefix but downstream-only → rebasebot identifies these via merge history and cherry-picks them. These MUST also be preserved.
5. Print the inventory summary (commit counts, file list) and proceed immediately to Phase 3.

### Phase 3: Execute Rebase
Run each repository individually (not using `--wave`). This gives full control to verify commits, trigger CI, and handle failures per repo. Always use `--working-dir` with a unique temp directory to isolate each run from stale state.

Repos within the same wave are independent of each other and can be rebased in any order. However, wave ordering must be respected: all repos in a wave must have their PRs merged before starting repos in the next wave.

**IMPORTANT: Use container mode (default) NOT `--local` mode.** The container image (`quay.io/migtools/rebasebot:latest`) includes Go and all required tools for hook scripts (`go mod tidy`, etc.). The `--local` mode requires Go to be installed on the host, which is not guaranteed. Only use `--local` if the user explicitly requests it or if container engines (docker/podman) are unavailable.

1. **Create a unique working directory**:
   ```bash
   WORK_DIR="/tmp/oadp-rebase-{repo}-$(date +%Y%m%d-%H%M%S)"
   ```

2. **Always dry-run first** (do NOT ask — just do it):
   ```bash
   ./run-oadp-rebase.sh --dry-run --working-dir "$WORK_DIR" --branch oadp-1.6 velero
   ```

3. **Analyze dry-run results automatically**:
   - **Success** → proceed to full run immediately (Phase 3 step 4)
   - **Failure due to `UPSTREAM: <drop>` conflicts in go.mod/go.sum** → This is the most common failure. The `<drop>` commits modify go.mod/go.sum which diverge between upstream versions. The strict conflict policy flags this as "content loss" but the content is regenerated by hooks. **Automatically retry with `--conflict-policy warn`**:
     ```bash
     # Temporarily override conflict policy for this run only
     # Do NOT modify the config file permanently — edit the config file, run, then revert
     WORK_DIR="/tmp/oadp-rebase-{repo}-$(date +%Y%m%d-%H%M%S)"
     ./run-oadp-rebase.sh --dry-run --working-dir "$WORK_DIR" --branch {branch} {repo}
     ```
     **CRITICAL: After the warn dry-run, scrutinize EVERY WARNING line in the output.** Categorize each warning:
     - Warnings about `go.mod` / `go.sum` lines → safe (regenerated by hooks)
     - Warnings about ANY other file → **STOP and report to user.** A downstream patch may be silently dropped.

     If ALL warnings are only about go.mod/go.sum → safe to proceed to full run with warn policy.
     If this also fails, check whether the error is still about go.mod/go.sum or about actual code conflicts.
   - **Failure due to stale rebase branch** ("dest already contains source") → Delete the stale branch and retry:
     ```bash
     gh api -X DELETE repos/oadp-rebasebot/{repo}/git/refs/heads/rebase-bot-{branch}
     ```
     Then re-run the dry-run.
   - **Failure due to code-level cherry-pick conflicts** → STOP and report to user. Show which commits conflict and which files are affected. Suggest `/oadp-rebase:manual-rebase` for manual intervention.

4. **Full run** (only after dry-run succeeds or conflict-policy-warn dry-run succeeds):
   ```bash
   WORK_DIR="/tmp/oadp-rebase-{repo}-$(date +%Y%m%d-%H%M%S)"
   ./run-oadp-rebase.sh --working-dir "$WORK_DIR" --branch oadp-1.6 velero
   ```
   If using conflict-policy warn, temporarily modify the config, run, then IMMEDIATELY revert:
   ```bash
   # Before run: temporarily add --conflict-policy warn to EXTRA_REBASEBOT_ARGS in config
   # After run: revert the config change (git checkout the file)
   # Do NOT commit the --conflict-policy warn change
   ```

### Phase 4: Post-Rebase Verification (AUTOMATED — do not ask, do not skip)
This phase MUST happen automatically after every successful rebase. If verification fails, do NOT proceed. This is the MOST IMPORTANT phase — a rebase that drops downstream content is worse than no rebase at all.

#### Step 1: Clone the rebase branch
```bash
git clone https://github.com/oadp-rebasebot/{repo}.git /tmp/oadp-verify-{repo}
cd /tmp/oadp-verify-{repo}
git checkout rebase-bot-{branch}
```

#### Step 2: Verify ALL downstream commits are preserved
Check for BOTH `UPSTREAM: <carry>` commits AND non-prefixed downstream commits:
```bash
# List all carry commits on rebase branch
git log --oneline --grep="UPSTREAM: <carry>" rebase-bot-{branch}
# List ALL commits (to find non-prefixed downstream ones too)
git log --oneline rebase-bot-{branch}
```

**Compare with the pre-rebase inventory from Phase 2.** Match by commit message subject line (not hash — hashes change during cherry-pick). For EVERY downstream commit saved in Phase 2:
- If it's an `UPSTREAM: <carry>` commit → it MUST appear in the rebase branch. If missing → **FAIL**.
- If it's a non-prefixed downstream commit → it MUST appear in the rebase branch. If missing → **FAIL**.
- If it's an `UPSTREAM: <drop>` commit → it's OK if missing (hooks regenerate these). But new `<drop>` commits from hooks should be present.

Print a clear comparison table:
```
COMMIT VERIFICATION:
  Expected carry commits: N
  Found carry commits:    N
  Missing carry commits:  [list any missing - CRITICAL]
  Expected non-prefixed:  N
  Found non-prefixed:     N
  Missing non-prefixed:   [list any missing - CRITICAL]
```

#### Step 3: Verify ALL downstream-only files exist
Using the file list saved in Phase 2, check EVERY downstream-only file:
```bash
# For each file in the Phase 2 downstream-only file list:
for f in Dockerfile.ubi konflux.Dockerfile .tekton release-announcement DOWNSTREAM_OWNERS; do
  if [ -e "$f" ]; then
    echo "OK: $f"
  else
    echo "MISSING: $f"
  fi
done
```

Also do a **reverse check** — look for files that were DELETED compared to the dest branch:
```bash
# Compare file trees between dest and rebase branch
git remote add dest https://github.com/{dest-org}/{repo}.git
git fetch dest {branch}
# Files in dest but not in rebase (potential drops)
diff <(git ls-tree -r --name-only dest/{branch} | sort) \
     <(git ls-tree -r --name-only rebase-bot-{branch} | sort) | grep '^<' | sed 's/^< //'
```
Any file that exists in dest but not in the rebase branch is a potential dropped downstream file. Investigate each one:
- If the file also doesn't exist upstream → it's a downstream-only file that was DROPPED → **FAIL**
- If the file exists upstream but was removed upstream → this is expected (upstream deletion)

#### Step 4: Verify hook-generated commits exist
This validates that post-rebase hooks ran successfully:
```bash
git log --oneline --grep="UPSTREAM: <drop>" rebase-bot-{branch}
```
There should be at least one `<drop>` commit per hook script that generates them (go-replace, go-mod-tidy, normalize-dockerfiles). If no `<drop>` commits exist, hooks may not have run — investigate.

#### Step 5: Final verdict
Print a clear summary:
```
REBASE VERIFICATION RESULT:
  Carry commits:         PASS/FAIL (N/N found)
  Non-prefixed commits:  PASS/FAIL (N/N found)
  Downstream files:      PASS/FAIL (N/N found)
  Hook commits:          PASS/WARN (N found)
  Deleted files check:   PASS/FAIL (N unexpected deletions)
  Overall:               VERIFIED / FAILED
```

- **ALL checks PASS** → print `VERIFIED` and proceed to Phase 5
- **ANY commit missing** → print `FAILED` with the exact missing commits, do NOT proceed, report to user
- **ANY downstream file missing** → print `FAILED` with the exact missing files, do NOT proceed, report to user
- **Unexpected file deletions** → print `FAILED` with the deleted file list, do NOT proceed, report to user

### Phase 5: Trigger CI
Rebase PRs are created by the `oadp-rebasebot` bot account. Most OADP repos require an authorized user to comment `/ok-to-test` on bot-created PRs before CI will run.

```bash
gh pr comment {pr-number} --repo {org}/{repo} --body "/ok-to-test"
```

Wait for CI to pass before merging. If CI fails, investigate before proceeding to the next wave.

### Phase 6: Follow-up Commits (if needed)
For version bump commits after velero rebase:
```bash
# In the rebase working directory, on the rebase branch:
# Update version in konflux.Dockerfile
sed -i 's/v1.18.0-OADP/v1.18.1-rc.1-OADP/' konflux.Dockerfile
git add konflux.Dockerfile
git commit -m "UPSTREAM: <carry>: update velero version to v1.18.1-rc.1"
git push
```

## Return Value
- **On success**: URL of the created PR on the rebase repository, plus verification summary
- **On dry-run**: Summary of what would be done, including commits to preserve and hooks to run
- **On failure**: Error details with automated remediation attempt, or clear report of what needs manual intervention

## Examples

1. **Rebase velero for oadp-1.6** (will automatically dry-run, verify, and handle conflicts):
   ```
   /oadp-rebase:rebase velero --branch oadp-1.6
   ```

2. **Dry-run only** (skip full run even if dry-run succeeds):
   ```
   /oadp-rebase:rebase velero --branch oadp-1.6 --dry-run
   ```

3. **Rebase AWS plugin for oadp-dev**:
   ```
   /oadp-rebase:rebase velero-plugin-for-aws --branch oadp-dev
   ```

4. **Rebase all Wave 3 repos one by one**:
   ```
   /oadp-rebase:rebase velero-plugin-for-aws --branch oadp-1.6
   /oadp-rebase:rebase velero-plugin-for-gcp --branch oadp-1.6
   /oadp-rebase:rebase velero-plugin-for-microsoft-azure --branch oadp-1.6
   /oadp-rebase:rebase velero-plugin-for-legacy-aws --branch oadp-1.6
   /oadp-rebase:rebase kubevirt-velero-plugin --branch oadp-1.6
   /oadp-rebase:rebase oadp-operator --branch oadp-1.6
   ```

## Arguments
- `$1`: Repository name (e.g., `velero`, `velero-plugin-for-aws`, `oadp-operator`)
- `--branch <branch>`: OADP branch to rebase (e.g., `oadp-1.6`, `oadp-dev`). Default: `oadp-dev`
- `--dry-run`: Execute in dry-run mode only (skip full run even if dry-run succeeds)
