# Manual Rebase Intervention

This skill documents specific failure modes and their manual remediation procedures.

## Failure Mode 1: Stale Rebase Branch

### When It Happens
- kubevirt-velero-plugin is the most common victim
- Occurs when:
  1. A rebase branch already exists on oadp-rebasebot/{repo}
  2. Rebasebot detects "dest already contains source" (upstream tag unchanged)
  3. Rebasebot starts hooks from the existing stale rebase branch instead of current dest
  4. Downstream-only files added after the stale branch was created are missing

### Symptoms
- PR shows deletion of Dockerfile.ubi, konflux.Dockerfile, release-announcement
- README.md regresses to upstream content
- .tekton/ directory missing
- PR has way more changes than expected

### Fix Procedure

```bash
# 1. Delete the stale remote rebase branch
gh api -X DELETE repos/oadp-rebasebot/{repo}/git/refs/heads/rebase-bot-{branch}

# 2. Clone the current downstream branch into a unique temp dir (this is the correct base)
WORK_DIR="/tmp/oadp-rebase-manual-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$WORK_DIR"
git clone https://github.com/{dest-org}/{repo}.git "$WORK_DIR/{repo}"
cd "$WORK_DIR/{repo}"
git checkout {branch}

# 3. Set up environment for hooks
export REBASEBOT_SOURCE="https://github.com/{upstream-org}/{repo}:{tag}"
export GIT_USERNAME="oadp-team-rebase-bot"
export GIT_EMAIL="oadp-maintainers@redhat.com"
git config user.name "$GIT_USERNAME"
git config user.email "$GIT_EMAIL"

# 4. Clone hook scripts (or use local copy from oadp-rebase repo)
git clone https://github.com/oadp-rebasebot/oadp-rebase.git /tmp/oadp-rebase-hooks
HOOKS_DIR="/tmp/oadp-rebase-hooks/rebasebot-hook-scripts"

# 5. Run each hook script in order (check the config file for the list)
# Example for kubevirt-velero-plugin:
bash $HOOKS_DIR/go-replace_velero_{branch}.sh
bash $HOOKS_DIR/go-mod-tidy-and-commit.sh
bash $HOOKS_DIR/normalize-dockerfiles-and-commit.sh

# 6. Push to rebase branch
git remote add rebase https://github.com/oadp-rebasebot/{repo}.git
git push rebase HEAD:rebase-bot-{branch} --force

# 7. Create PR
gh pr create --repo {dest-org}/{repo} \
  --base {branch} \
  --head oadp-rebasebot:rebase-bot-{branch} \
  --title "Rebase {repo} to {tag}" \
  --body "Manual rebase - ran hooks on current dest branch to update dependencies."

# 8. VERIFY carry commits and downstream files
git log --oneline --grep="UPSTREAM: <carry>" HEAD
ls -la Dockerfile.ubi konflux.Dockerfile release-announcement .tekton/ 2>/dev/null
```

### Important Notes
- Even after deleting the stale branch and re-running rebasebot, the same problem may recur if rebasebot's "dest already contains source" logic still triggers
- The most reliable fix is the manual procedure above: start from dest, run hooks, push

## Failure Mode 2: Strict Conflict Policy Blocking

### When It Happens
- Usually during Wave 3 plugin rebases
- Strict policy detects go.mod/go.sum "content loss" from `UPSTREAM: <drop>` commits
- The "lost" content is upstream transitive dependencies that `go mod tidy` will regenerate

### Symptoms
- Rebasebot error: `ERROR - Manual intervention is needed`
- Error mentions specific go.mod/go.sum lines being lost
- The lost lines are typically `require` or `replace` directives for upstream dependencies

### Verification Before Override
Before using `--conflict-policy warn`, verify the flagged content is safe to lose:

1. Check if the "lost" lines are from `UPSTREAM: <drop>` commits:
   ```bash
   git log --all --oneline -- go.mod | head -10
   git show {commit}:go.mod | grep "{lost-dependency}"
   ```

2. Verify the content will be regenerated by `go mod tidy` (it's an upstream transitive dependency, not a downstream security fix)

3. If the content IS a downstream security fix (pinned version override), do NOT use `--conflict-policy warn` - manually resolve the conflict instead

### Fix Procedure

```bash
# 1. Temporarily add --conflict-policy warn to the config
# Edit rebase-configs/{config}.env.sh:
EXTRA_REBASEBOT_ARGS="--always-run-hooks --conflict-policy warn"

# 2. Run the rebase
./run-oadp-rebase.sh --local --branch {branch} {repo}

# 3. IMMEDIATELY revert the conflict policy change
# Edit rebase-configs/{config}.env.sh:
EXTRA_REBASEBOT_ARGS="--always-run-hooks"

# 4. Verify ALL carry commits are preserved
git log --oneline --grep="UPSTREAM: <carry>" rebase-bot-{branch}

# 5. Do NOT commit the --conflict-policy warn change to the repo
```

### Critical Warning
NEVER leave `--conflict-policy warn` in the config file permanently. It disables an important safety check. Only use it temporarily for a single rebase run, then revert.

## Failure Mode 3: hypershift-oadp-plugin

### Why It's Always Manual
- Not included in wave automation
- Uses a personal fork for PRs (not oadp-rebasebot)
- Only needs go.mod replace directive update (no actual rebase)
- Requires `go mod vendor` which can be slow

### Procedure

```bash
# 1. Find the latest commit on downstream velero branch
VELERO_COMMIT=$(gh api repos/openshift/velero/commits?sha={branch}&per_page=1 \
  --jq '.[0].sha')
echo "Latest velero commit: $VELERO_COMMIT"

# 2. Clone hypershift-oadp-plugin into a unique temp dir
WORK_DIR="/tmp/oadp-rebase-hypershift-$(date +%Y%m%d-%H%M%S)"
git clone https://github.com/openshift/hypershift-oadp-plugin.git "$WORK_DIR"
cd "$WORK_DIR"

# 3. Update go.mod replace directive
# First check which module path the project uses:
grep "velero" go.mod | head -5
# Use the matching path (vmware-tanzu or velero-io) on the left side:
go mod edit -replace github.com/vmware-tanzu/velero=github.com/openshift/velero@${VELERO_COMMIT}

# 4. Tidy and vendor
go mod tidy
go mod vendor

# 5. Verify compilation
go vet ./...

# 6. Check the pseudo-version that was generated
grep "openshift/velero" go.mod

# 7. Create branch, commit, push, PR
git checkout -b update-velero-dep
git add -A
git commit -m "UPSTREAM: <carry>: update velero dependency to latest oadp-{branch}"
git push origin update-velero-dep
gh pr create --base main --title "Update velero dependency" \
  --body "Updates go.mod replace directive to point to latest openshift/velero {branch} commit."
```

### Go Pseudo-Version Note
When you run `go mod tidy` after `go mod edit -replace ...@{commit}`, Go will resolve the commit to a pseudo-version like:
```
v0.10.2-0.20260504131308-8373027be9ec
```
Format: `v{base}-0.{YYYYMMDDHHMMSS}-{12-char-hash}`

## Failure Mode 4: Cherry-Pick Conflicts

### When It Happens
- Upstream changes conflict with downstream carry commits
- Usually in go.mod, go.sum, or files modified by both upstream and downstream

### Procedure
1. Clone the working directory and attempt manual cherry-pick:
   ```bash
   git cherry-pick {carry-commit-hash}
   # Resolve conflicts
   git add -A
   git cherry-pick --continue
   ```
2. For go.mod/go.sum conflicts:
   - Accept the upstream version
   - Re-run `go mod tidy` to regenerate
   - The hook scripts will handle the rest
3. For code conflicts:
   - Understand what the carry commit does
   - Adapt it to the new upstream code
   - Preserve the intent of the downstream patch

## Failure Mode 5: Hook Script Failure

### Common Causes
- Missing dependency repo (wave ordering violated)
- Network issues fetching dependencies
- `go mod tidy` failure due to incompatible versions
- `make bundle` failure in oadp-operator

### General Debugging
```bash
# Run the failing hook manually with verbose output
bash -x $HOOKS_DIR/{hook-script}.sh

# Check if REBASEBOT_SOURCE is set
echo $REBASEBOT_SOURCE

# For go mod tidy failures, check what's in go.mod
cat go.mod | grep -A5 "replace"

# For CRD copy failures, check if velero branch exists
gh api repos/openshift/velero/branches/{branch} --jq '.name'
```
